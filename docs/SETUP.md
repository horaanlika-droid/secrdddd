# дибитишка · запуск за 5 шагов

Приложение: `app/` (статика → GitHub Pages + Telegram Mini App).
Бот: `bot/` (Node.js, grammY) — контент, рассылки, коды входа, пуши, Tribute.

## 1. Бот-хост: ровно три переменные

| переменная | что вписать |
|---|---|
| `TG_TOKEN` | токен бота от @BotFather |
| `ADMIN_IDS` | id админов через запятую, напр. `111111,222222` |
| `TRIBUTE_API` | ключ Tribute API для бизнеса. **Можно вписать позже** — до этого пейвол честно говорит «оплата подключается» |

Четвёртая, для «живой» Дибитишки: `OPENAI_API_KEY` — ключ OpenAI. **Тоже можно вписать
позже**: без него бот и веб-чат отвечают шаблонами и честно пишут, что живой чат подключается.
Вписал ключ, перезапустил бота — Дибитишка отвечает сама (в Телеграме на любое сообщение,
в вебе — во вкладке «Чат», с памятью о записях пользователя). Необязательно: `OPENAI_MODEL`
(по умолчанию `gpt-4o-mini`), `OPENAI_BASE_URL` (совместимый прокси). Промпт — `bot/src/persona.js`.
Проверить: админ пишет боту `/ai`, или `GET /health` → `"ai": true`.

Необязательно: `PORT` (по умолчанию 8080) — если хостинг даёт порт, бот поднимет HTTP API
и веб-версия получит живой контент, проверку кодов входа и синхронизацию напоминаний.

Запуск: `npm install && npm start` в папке `bot/`.
(Забыл `npm install` — не страшно: бот сам поставит недостающее при старте, см. ниже.)

### Или в Docker (рекомендуется, если бот живёт в контейнере)

Всё, что нужно боту (grammy, jpeg-js, pngjs), ставится при сборке образа —
зависимости не теряются при перезапуске/пересборке:

```bash
cp .env.example .env   # вписать TG_TOKEN, ADMIN_IDS, (TRIBUTE_API)
docker compose up -d --build
docker compose logs -f # смотрим, что [bot] polling started
```

Данные (пользователи, контент, напоминания) лежат в томе `bot-data` (`/data/db.json`) —
переживают пересборку. Без compose: `docker build -t dibitishka-bot .` и `docker run`
(см. комментарий в `Dockerfile`).

> **Про `ERR_MODULE_NOT_FOUND: Cannot find package 'grammy'`**
>
> Раньше эта ошибка означала перезапуск контейнера по кругу: статический
> `import { Bot } from 'grammy'` стоял первой строкой точки входа, и процесс
> умирал до того, как выполнялась хоть одна наша строчка.
>
> Теперь это закрыто в коде, терминал не нужен:
>
> 1. **Точка входа ничего не импортирует.** `bot/src/index.js` сначала зовёт
>    `bot/src/ensure-deps.js`, и только потом грузит приложение (`bot/src/app.js`).
> 2. **Бот ставит зависимости сам.** Если grammy/pngjs/jpeg-js не резолвятся,
>    `ensure-deps` пробует по очереди: `npm ci` → `npm install` → `npm install <пакеты>`
>    в `bot/`, то же в корне репозитория, а если папка доступна только на чтение —
>    ставит во временную папку и подключает её через ESM-хук. В логе это выглядит так:
>    ```
>    [deps] не хватает: grammy, jpeg-js, pngjs
>    [deps] ставлю сам — терминал не нужен
>    [deps] пробую: npm ci (bot/)
>    [deps] готово: grammy, jpeg-js, pngjs
>    [http] API on :8080
>    ```
> 3. **Сборка образа не проходит без зависимостей.** В `Dockerfile` после `npm ci`
>    стоит `node bot/src/ensure-deps.js --check`, а затем `node scripts/smoke.mjs` —
>    образ реально поднимается и отвечает на `/health` ещё до деплоя.
>
> Если бот всё же не стартует и в логе `[deps] ✗` — значит npm не смог поставить
> пакеты (обычно нет сети или нет прав на запись). Тогда один раз вручную:
> ```bash
> cd bot && npm ci && npm start
> # или пересобрать образ без кэша
> docker compose down && docker compose build --no-cache && docker compose up -d
> ```

### Авто-очистка порта при деплое

Перед тем как занять `PORT`, бот проверяет, не держит ли его процесс с прошлого
запуска (оставшийся `npm start`, не умерший до конца контейнер). Держателя он
находит сам — на Linux через `/proc/net/tcp` + `/proc/<pid>/fd`, без lsof/fuser
и без доустановки чего-либо, — и останавливает: SIGTERM, ждёт до 3 секунд,
не отпустил — SIGKILL. После этого новый деплой занимает порт с первого раза
и не падает в `EADDRINUSE`. В логе это выглядит так:

```
[port] порт 8080 занят (pid 42137) — останавливаю, чтобы новый запуск занял порт
[port] порт 8080 освобождён до старта: pid 42137
[http] API on :8080
```

Если бот всё же не может занять порт (держателя не видно или нет прав на
остановку) — он честно напишет, как освободить вручную: `fuser -k 8080/tcp`.
Не хочешь, чтобы бот трогал чужие процессы: `NO_PORT_CLEAN=1` — тогда займёт
порт только если тот свободен, иначе упадёт с ошибкой (старое поведение).

### Проверки (чтобы это не вернулось)

```bash
npm run check   # зависимости резолвятся, lockfile не разошёлся, точка входа
                # не импортирует grammy напрямую, .dockerignore ничего не потерял,
                # корень Pages ведёт в app/, порт чистится через acquirePort
npm run smoke   # бот реально поднимается и отвечает на /health и /content.json
npm run port    # деплой на занятый порт: своя копия уходит, чужая не страдает
npm run verify  # всё вместе
npm run ai-check# «почему чат молчит»: ключ, модель, getMe, живой /health и /chat
npm run ai-test # живой чат против подставного OpenAI (400/429/404/таймауты), без сети
```

То же самое делает CI: `.github/workflows/ci.yml` на каждый пуш и PR.
Отдельная джоба `self-heal` воспроизводит аварию — удаляет `node_modules`
и проверяет, что бот поставит их сам и поднимется. А `pages.yml` после публикации
открывает сайт и проверяет, что там приложение, а не README.

## 2. GitHub Pages

1. В репозитории: Settings → Pages → Build and deployment → Source: **GitHub Actions**.
2. Пуш в `main` — workflow `.github/workflows/pages.yml` опубликует папку `app/`
   и сам проверит, что по адресу открывается приложение, а не README.
3. URL вида `https://<user>.github.io/<repo>/` — это веб-версия.

> Если source почему-то стоит **«Deploy from a branch»** (ветка `main`, корень)
> — ничего страшного: на корне лежит `index.html`, который автоматически ведёт
> в `/app/`. Сайт больше не открывается как отрендеренный README — и там,
> и здесь по URL открывается приложение.

1. @BotFather → `/newbot`, забрать токен в `TG_TOKEN`.
2. @BotFather → `/newapp` (или Bot Settings → Menu Button) → указать URL Pages.
   В Телеграме приложение откроется как Mini App с автовходом; снаружи — войдёт по коду.

пуши и синхронизация работают. Код одноразовый, живёт 10 минут.

## 5. Tribute после запуска

Как устроено: ссылки на оплату бот не «создаёт запросом», а берёт готовыми из
кабинета Tribute. Ты создаёшь три цифровых товара (по одному на тариф), бот
отдаёт их ссылки кнопкой «💳 Оплатить», а после оплаты Tribute сам стучится
на `https://<адрес бота>/tribute/webhook` — бот проверяет подпись и активирует
подписку. Подробности — в шапке `bot/src/tribute.js` и [вики Tribute](https://wiki.tribute.tg).

1. **Товары.** Открой [@tribute](https://telegram.me/tribute) → Author Dashboard →
   Digital Products → Create instant product. Создай три товара:
   «Дибитишка · 1 месяц» — 200 ₽, «3 месяца» — 500 ₽, «6 месяцев» — 900 ₽.
   В текст товара впиши, что доступ активируется автоматически и надо вернуться
   в бота. У каждого товара скопируй ссылку вида `https://t.me/tribute/app?startapp=p123`.
2. **Переменные на бот-хосте** (см. `.env.example`):
   `TRIBUTE_M1_URL` / `TRIBUTE_M3_URL` / `TRIBUTE_M6_URL` — три ссылки из шага 1
   (или одна общая `TRIBUTE_PAY_URL`, если товар пока один);
   `TRIBUTE_API` — ключ из кабинета (меню → Settings → API Keys), он нужен для
   проверки подписи вебхуков; необязательно `TRIBUTE_PRODUCT_DAYS=456=30,457=90,458=180`
   (id товаров → дни; без него каждый вебхук даёт 30 дней, а у подписок срок
   берётся из `expires_at`). Перезапусти бота.
3. **Вебхук.** В том же разделе API Keys впиши Webhook URL:
   `https://<адрес бота>/tribute/webhook`.
4. **Проверка.** Админ пишет боту `/tribute` — там видно, что настроено, а что нет
   (бот сам проверяет ключ у Tribute). Или `GET /health` → поле `tribute`.
5. Готово: `/pay` в боте, deep-link `?start=pay_m1` и кнопка «Оплатить в Telegram»
   в вебе отдают ссылку Tribute; вебхук активирует подписку сам — даже если человек
   оплатил раньше, чем нажал `/start` (бот заведёт его в базе из вебхука).

> Если кнопка «Оплатить в Telegram» в вебе упирается в «такого пользователя
> не существует» — это не Tribute, а `bot_username` в `app/config.js`: там всё ещё
> заглушка. Впиши реальный username бота из @BotFather (без @), сделай коммит —
> Pages пересоберётся за минуту.

> Редкий режим: вместо статичных ссылок бот может создавать заказы сам через
> Shops API (`POST /api/v1/shop/orders`) — включи `TRIBUTE_SHOP=1` (нужен
> настроенный магазин Tribute, `TRIBUTE_SHOP_ID` — если их несколько).

## Контент: актуализация любого блока

- С портом: админ пишет боту `/content set blocks.0.title Новое имя` — веб подтянет сразу.
  Пути любые: `blocks.N.…`, `blocks.N.practices.M.…`, `meta.…`, `merch.…`, `workbook.…`.
- Без порта: `/export` присылает `content.json` файлом → положи его в `app/content/content.json`
  и сделай пуш (Pages пересоберётся за минуту). `/import` — загрузка файла обратно в бота.
- Рассылки: `/broadcast` → следующее сообщение админа = черновик (текст и/или картинка).
  У картинок с белым фоном бот предложит «вырезать белый фон» — картинка будет парить над чатом.
- Пуши: пользователь `/reminder 9:00 +3` — бот шлёт практику дня с картинкой маскота ежедневно.

## Чат молчит: найти причину за минуту, а не гадать

Симптом «ии чат до сих пор не реагирует» может означать три разные поломки,
и снаружи они выглядят одинаково. Разделение такое:

| что молчит | где смотреть | как чинить |
|---|---|---|
| бот в Telegram | `GET /health` → `telegram.polling` | `running` + `updates: 0` → пишешь не тому боту; `poll_error: conflict` → polling держит старая копия |
| чат в вебе | `GET /chat/status` → `ai`, `problems[]` | `ai: false` → на хосте нет `OPENAI_API_KEY` |
| живой голос (OpenAI) | `ai_health` → `last_error` | см. таблицу ошибок ниже |

Одна команда делает всё это разом:

```bash
npm run ai-check                                   # на бот-хосте, рядом с .env
npm run ai-check -- --url https://<адрес-бота>     # из любой точки — против живого хоста
```

Или прямо в Telegram, админу: **`/diag`** (кратко — `/ai`).

### `polling: retry|dead`, `poll_error: conflict`

Telegram отдаёт апдейты **одному** получателю. Если где-то ещё живёт копия
этого же бота (старый контейнер, `npm start` в другой папке, прошлый деплой,
который не умер), новая копия вечно ловит `409 Conflict`: HTTP API отвечает,
`/health` говорит `ai: true`, а на сообщения — тишина. Это ровно тот случай,
когда «ключ поправили, а чат всё равно молчит».

```bash
docker ps                                  # найти старый контейнер
pgrep -af "bot/src/index.js"               # найти процесс-зомби на хосте
docker restart dibitishka-bot              # или остановить то, что нашлось
```

С 2026-09-15 процесс сам вежливо освобождает порт от СВОЕЙ прошлой копии
(`bot/src/port.js`) и корректно закрывается по SIGTERM (`сохраняю базу и
освобождаю порт`) — так старый деплой не должен переживать новый. Чужие
процессы не трогаются никогда: при чужом порте бот уходит на PORT+1 и
пишет об этом в лог (тогда обнови `bot_public_url` в `app/config.js`).

### `poll_error: auth`

`TG_TOKEN` не принят. Чаще всего это токен **другого** бота: сверь `@username`
из `npm run ai-check` (или из `telegram.as` в /health) с тем, кому ты пишешь.

### `users: 0` при живом HTTP

Два варианта: сообщения читает другая копия (см. `conflict`), или база не
переживает рестарт. В Docker нужен том: `-v dibitishka-data:/data`
(в `docker-compose.yml` он есть). В `ai-check` это отдельная строка
«база лежит в /tmp» — данные там живут до перезапуска контейнера.

### `NO_POLLING=1`

С этой переменной работает только HTTP API (так бота поднимают смоук-тесты
и CI). На боевом хосте её быть не должно — иначе Telegram молчит всегда.

### Ошибки OpenAI: что значит `ai_health.last_error`

| код | что это | что делать |
|---|---|---|
| `no_key` | переменной нет | вписать `OPENAI_API_KEY`, перезапустить |
| `bad_key` | 401, ключ не принят | перевыпустить ключ; проверить кавычки/пробелы; для ключа проекта — `OPENAI_PROJECT` |
| `no_quota` | 429 `insufficient_quota` | **пополнить баланс** — это не «перегрузка сервера» |
| `rate_limit` | 429, настоящий лимит | подождать; при долгих лимитах — второй ключ/проект |
| `bad_model` | 404 `model_not_found` | поправить `OPENAI_MODEL` |
| `bad_param` | 400 `Unsupported parameter` | бот подхватит сам: уйдёт на `max_completion_tokens` без `temperature` |
| `too_long` | контекст не влезает | уменьшить `AI_HISTORY` |
| `geo_blocked` | 403 регион | сменить сеть/прокси на хосте |
| `timeout` / `network` | хост не достучался до API | проверить сеть/DNS; потолок — `OPENAI_TIMEOUT_MS` |

Полезно знать: `ai: true` в /health означает только «переменная `OPENAI_API_KEY`
не пустая». Что ключ рабочий, модель существует, а на аккаунте есть деньги —
это уже `ai_health.last_error` или `/diag`.

## Агенты: сессия и self-hosted окружение (необязательно)

По умолчанию чат ходит в `chat/completions` (`bot/src/ai.js`): один запрос —
один ответ, ничего не крутится между репликами. Это правильный режим для
«мне тяжело сейчас».

Второй бэкенд — [Agents API](https://developers.openai.com/api/docs/guides/agents-api/overview):
у диалога появляется **сессия** (память треда живёт на стороне API) и
**окружение**, где агент читает файлы, запускает код и работает инструментами
(`bot/src/agents.js`). Включать стоит, если Дибитишке правда нужны тетрадь
в файлах, репозиторий или длинные многошаговые задачи. Для чата поддержки —
обычно нет: это лишние деньги (контейнерное время), лишние scope'ы ключа и
песочница, в которой крутится код от модели.

### 1. Ключ приложения: права

`OPENAI_API_KEY` должен иметь `api.agents.read`, `api.agents.write` и
`api.responses.write`. Без них создание сессии отвечает 403 — в логе и в
`/diag` это видно как `agents: auth`.

### 2. Ключ окружения (отдельный!)

platform.openai.com/agents → **Environments → Keys** → создать ключ, у которого
разрешено только подключение окружения, всё остальное — **None**. На бот-хосте:

```
OPENAI_EXECUTOR_API_KEY=sk-env-...   # бот передаст его исполнителю как CODEX_API_KEY
```

Ключ приложения в песочницу не уходит: `bot/src/agents.js` собирает процессу
исполнителя только `PATH`, `HOME`, `CODEX_API_KEY` (плюс то, что ты сам
перечислишь в `AGENTS_EXECUTOR_ENV`).

### 3. Исполнитель окружения

Внутри окружения (контейнер, ВМ, та же машина в изоляции) должен стоять Codex CLI:

```bash
mkdir -p /workspace && npm install -g @openai/codex@alpha
```

Наружу разрешены `https://api.openai.com` (регистрация) и
`wss://codex-cloud-environments.chatgpt.com` (команды и результаты) — все
соединения исходящие, реверс-прокси окружению не нужен.

### 4. Переменные на бот-хосте

```
AGENTS_ENABLED=1
AGENTS_MODEL=gpt-4o-mini
AGENTS_WORKSPACE=/workspace
AGENTS_EXECUTOR_CMD=codex exec-server --remote "{remote_url}" --environment-id "{environment_id}"
```

`{remote_url}` и `{environment_id}` подставляет сам бот из ответа
`POST /v1/agents/sessions` — **их нельзя захардкодить**: у каждой сессии своё
окружение и свой исполнитель. Поэтому пара вида

```
codex exec-server --remote "https://api.openai.com/v1/agents/api/connect/rt_xxxx" \
                  --environment-id "ccarenv_b64_..."
```

из доков/showcase — это **одна конкретная** сессия, созданная ранее. Ручной
запуск такой команды годится только для проверки «вот оно живёт»; как только
сессию закроют или она протухнет, исполнитель подключится не сможет, и чат
будет висеть до `AGENTS_TURN_TIMEOUT_MS`. Правильно — чтобы команду запускал
бот (`AGENTS_EXECUTOR_CMD`), либо чтобы ты видел актуальные значения в
`/diag` (там `session_id`, состояние окружения и pid исполнителя).

Не задаёшь `AGENTS_EXECUTOR_CMD` — бот не трогает процессы, а пишет готовую
команду в лог и в `/diag`; тогда запускай её вручную в нужном окружении.
Токен из `remote_url` бот нигде целиком не печатает (`connect/rt_***`), и в
`/health` он не попадает.

### 5. Как это выглядит в рантайме

```
[agents] сессия ses_01ABC для «tg:123» · окружение ccarenv_b64_***
[agents] исполнитель запущен: pid 4213 для окружения ccarenv_b64_***
```

Состояния окружения: `pending` (ждём исполнителя) → `connected` (агент
набирает ход) → `failed` (не подключился). Если окружение так и не пришло,
бот не молчит: ход прерывается с `environment_pending` / `environment_failed`,
человек получает тёплый ответ из своих записей, а владелец — причину.

В `/health`:

```json
"agents": { "enabled": true, "sessions": 3, "turns": 41, "fallbacks": 0,
            "executor_cmd": true, "executor_key": true, "last_error": null,
            "live": [{ "key": "tg:123", "session_id": "ses_01…", "environment_state": "connected",
                       "executor": "работает (pid 4213)", "idle_s": 12 }] }
```

### 6. Откат

`AGENTS_ENABLED=0` + перезапуск — чат снова только на `chat/completions`.
Сессии на стороне OpenAI при закрытии процесса удаляются (`closeAllSessions`
по SIGTERM), `reset` в Telegram закрывает сессию диалога сразу.

## Доски впечатлений: синхронизация и фото (итерация 26)

В приложении: **Доски → Синхронизация с Telegram → Включить синхронизацию**.
По умолчанию доски остаются локальными. Для веб-входа нужен новый одноразовый
`/code`: старые привязки v25 содержали только ID, не доказательство входа.
В Mini App используется подписанный `Telegram.WebApp.initData` (срок 24 часа);
если он устарел, достаточно заново открыть Mini App из Telegram.

### Постоянное хранилище

- `BOARDS_DATA_DIR` — по умолчанию `board-data/` рядом с `DB_FILE`.
  В Docker Compose это `/data/board-data`, уже покрытый томом `bot-data`.
- Метаданные и ревизии записываются атомарно, отдельно по аккаунтам.
  Фото по умолчанию лежат в этом же каталоге, не в `db.json`.
- При обычном хостинге **смонтируй постоянный диск** для `DB_FILE` и
  `BOARDS_DATA_DIR`. Временная файловая система переживёт смену телефона, но
  не пересоздание контейнера — это не резервная копия. Делай резервные копии
  базы и каталога досок вместе.
- Необязательное объектное хранилище: `BOARDS_S3_ENDPOINT`, `BOARDS_S3_BUCKET`,
  `BOARDS_S3_REGION` (`auto` для R2), `BOARDS_S3_ACCESS_KEY`, `BOARDS_S3_SECRET_KEY`.
  Поддерживается S3 path-style / AWS Signature V4. Бакет должен быть **закрытым**;
  ключу нужны GetObject/PutObject/DeleteObject только в этом бакете.
  Неполная конфигурация отключает приватный API, а не переключает фото молча
  в другое хранилище. Даже при S3 метаданные и веб-сессии остаются на постоянном
  диске. Живой бакет надо проверить с реальными настройками хоста.
- `BOARDS_ENABLED=0` отключает серверную синхронизацию, локальные доски работают.
- Квоты на аккаунт: 60 досок, 400 плиток на доску / 2000 суммарно,
  6 МБ на файл, 100 МБ медиа. Невостребованные файлы удаляются после недели
  при следующей операции записи. Удаление плитки не удаляет фото, используемое
  как фон. Очистка пользовательских данных на сервере: каталог конкретного
  аккаунта в `BOARDS_DATA_DIR` и его префикс в S3; выключение автосинхронизации
  само по себе данные не удаляет.

### Контракт и приватность

- `GET /board/status` — доступность, без личных данных.
- `GET /board` — `{revision, boards, media}` только своего аккаунта.
- `POST /board` — `{base_revision, boards}`. Устаревшая ревизия → `409`, веб
  перечитывает и объединяет изменения. Конфликтующие тексты сохраняются обеими
  версиями, а не выбираются по неверным часам телефона.
- `POST /board/media/<key>` / `GET /board/media/<key>` — приватные изображения;
  подпись содержимого, ограничение объёма, только JPEG/PNG/WebP/GIF, не SVG/HTML.
- Вход: `Authorization: tma <подписанный initData>` либо `Bearer <session>`,
  выдаваемый `/auth/verify` после одноразового кода. ID из URL/JSON не даёт доступ.
  Сессии живут 30 дней, в базе — только их хеши. Код `/code` генерируется
  криптографически, попытки входа ограничены. Секреты не попадают в `/health`.
- При публикации Pages веб ходит по `bot_public_url`; бот, который сам отдаёт
  приложение, принудительно использует свой origin. CORS разрешает заголовок
  `Authorization`. Не открывай `BOARDS_DATA_DIR` статическим веб-сервером.
- Доски разных аккаунтов в браузере разделены. Перенос гостевых досок в аккаунт
  предлагается явно и не выполняется без отметки человека.

## GIF-поиск в приложении

Задай **`TENOR_API_KEY` только на сервере бота**, затем перезапусти бот.
Веб использует `GET /gif?q=...`, не знает ключ и показывает источник Tenor.
Есть ограничение частоты, короткий кеш, таймаут, безопасный фильтр контента.
Без ключа или при недоступности Tenor работают ручная HTTPS-ссылка и переход
в поиск Tenor. Экспорт ограничен 12 страницами за раз, чтобы не перегрузить память телефона;
большую доску надо разделить (данные не обрезаются молча).
В экспорт GIF попадает неподвижным кадром; если сервер GIF
запрещает CORS, экспорт покажет заглушку и предупредит об этом.

для промежуточных кадров маскота. Большие временные исходники генераций — `_source/`.
